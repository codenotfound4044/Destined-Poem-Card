# 版本、封面与发布

## 版本号规则

| 变动 | 什么时候用 | 世界书名 |
| --- | --- | --- |
| 0.0.1（patch） | 兼容旧存档的改动 | 不变 |
| 0.1（minor） | 不兼容旧存档：变量结构等硬性变化，玩家要手动改变量 | 改 |
| 1（major） | 世界观大改 | 改 |

这是开发组的习惯，具体发什么版本号由开发组决定。平时改变量、改世界观都不动版本号和名字，只有明确要发布时，才按开发组给的版本号改；工具和 AI 只给建议。

版本号只写在 [release.json](../release.json) 的 `version` 里，`releasedAt` 记录发布时间。卡名、世界书名和发布标签都由它和 `cardName` 算出来（[tools/lib/version.mjs](../tools/lib/version.mjs)）：卡名和世界书名只带前两位，比如 `命定之诗与黄昏之歌v4.3`，标签是 `v4.3.4`。`card/meta.json` 里的名称字段会被覆盖；作者备注里写 `{{版本}}`，构建时会换成版本号。

## 开发版

两次发布之间，推到酒馆测试的都是 local 构建，版本号是 `V4.3.3+dev.20261024.a7e44eb`，意思是“4.3.3 之后的开发版”。末尾 7 位取自不含版本号的卡内容哈希，同一份内容推几次都一样。卡名和世界书名不变，测试推送不会多出新的世界书。release 构建用正式版本号。

## 世界书版本标记

构建时，世界书末尾会加一条不启用的条目「【版本标记】请勿修改」，内容就是卡的版本号。自动化脚本（[worldbook-check.ts](../packages/automation/src/runtime/worldbook-check.ts)）在启动和切换聊天时，拿它和角色卡的 `character_version` 比较。对不上（包括 4.3.3 及更早没有标记的世界书）就弹窗，玩家可以：

- 「更新世界书」：先把旧世界书另存为「名称（旧版本 备份 时间）」，再用卡里自带的世界书替换。
- 「这次先不更新」。
- 「这个版本不再提醒」：只对当前这对版本生效，下一版还会提示。

这样玩家沿用同名旧世界书时，补丁更新的内容也能进去，不用先删旧世界书。

## 封面

封面是 [card/cover/cover.png](../card/cover/cover.png)，只认这一个 PNG 文件。构建时会去掉图片里原有的文字块（比如旧卡数据），把卡数据写进去，生成 `dist/<profile>/命定之诗与黄昏之歌.png`。缺封面时构建会失败。可以在工作台「推送到酒馆」页更换，旧封面会留在 `.cache/workbench/covers/`。推送到酒馆时会用它替换目标卡的头像，详见 [推送到酒馆](sync.md)。

## 更新记录与发版

改了玩家能感知的东西，就在 [CHANGELOG.md](../CHANGELOG.md) 的「未发布」下面记一条；不兼容旧存档的条目开头加【不兼容】。也可以在工作台「版本与发布」页编辑。

```sh
pnpm card version            # 和上一版比：变量结构变化、建议升哪一位
pnpm card release 4.3.4      # 填开发组定好的版本号；patch / minor / major 也行
```

`version` 会重新导出变量结构，和 `card/releases/V<上一版>.schema.json` 对比：

- 新增带默认值的字段算兼容；
- 删除字段、改类型、新增必填字段、可选值变少算不兼容；
- 只改了约束或默认值的标成“需确认”。

版本号由开发组决定，工具只给建议：有不兼容变化或【不兼容】条目时会提醒「按习惯一般升 0.1」，但不会拦着。新版本号必须比当前大。

`release` 会依次：

1. 改 `release.json` 的版本号和时间；
2. 保存新的变量结构快照；
3. 把「未发布」移到新版本标题下；
4. 构建 local 和 release，并做产物校验；
5. 在 `dist/release/发布包/` 生成 `命定之诗与黄昏之歌V4.3.4.png` 和 `更新说明.txt`。更新说明里会按是否改了世界书名，写清玩家怎么更新。

中途失败会还原版本号、更新记录和快照。

发版只在本机进行，不提交、不打标签、不推送。release 卡的程序资源从 `Destined-Poem-Card@assets-v<资源版本>` 加载（见下文「程序资源版本」）；正式发卡时如果程序也有改动，同一个提交一起打卡标签和资源标签。打标签和发布 `dist/release/**` 的要求见 [工作流](workflow.md)。

V4.3.3 于 2026-09-12 14:55 在社区发布。它的变量结构快照取自前端仓库标签 `v1.9.26`（同日 13:06，是发布前最后一个标签）。之后工作区里的改动都属于下一版。

## 程序资源版本

前端（首页、状态栏、自定义开局、Schema 注册）、自动化和地理加载脚本共用一套程序资源版本，和卡版本分开，记在 `release.json` 的 `assets` 里：

```json
"assets": {
  "version": "1.0.0",
  "tagPrefix": "assets-v",
  "published": false,
  "cdnOrigins": ["https://testingcf.jsdelivr.net", "https://cdn.jsdelivr.net", "https://fastly.jsdelivr.net", "https://gcore.jsdelivr.net"]
}
```

CDN 地址是 `<cdnOrigin>/gh/<仓库>@assets-v<资源版本>/dist/release/...`。release 构建和"推 CDN 资源"都用它；卡版本只决定卡名、世界书名和卡的标签 `v<卡版本>`。只修程序时发资源补丁，卡版本不动。

### 卡里的加载器

三条界面正则、三个自有脚本（Schema 注册、自动化、地理数据）和三个第三方脚本（创意工坊、自动正则、角色管理库）不再写死单个 URL，而是内嵌同一段加载代码（源码在 [tools/lib/resource-loader.mjs](../tools/lib/resource-loader.mjs)）：

- 按 `cdnOrigins` 的顺序探测入口文件（每个最多等 6 秒），用第一个能连上的；成功的那个记在浏览器 `localStorage`，下次先试它。
- 角色变量「资源版本」是一个对象，每组脚本一项：`{ 命定之诗: "1.0.0", 创意工坊: "2.3.1", 自动正则: "2.3.1", 角色管理库: "0.3.7" }`。「命定之诗」管自有的界面、自动化和地理脚本，默认值是 `assets.version`；三个第三方脚本的默认值取 `release.json` 的 `dependencies` 链接里的版本，版本前的 `v` 由加载器补，玩家填不填都行。每组各读自己那一项，没填就用卡内默认版本。填的版本在所有 CDN 上都加载不到时，退回默认版本并提示一次；格式不对（不是 `主.次.补丁`）同样提示并用默认版本。
- 前端页面从加载器设置的 `__destinyAssetBase` 取数据和图片地址，所以数据文件也跟着走同一个 CDN。
- 本机构建（local）的自有资源只有 `http://127.0.0.1:5173/dist/local` 一个地址，不读「命定之诗」那一项；第三方脚本照常走 CDN 和版本设置。
- 实际加载的版本和卡内默认版本记在浏览器 `sessionStorage`（`destiny:loaded:<名称>`），状态栏设置页据此显示。

玩家在状态栏「设置」页的「脚本版本」里改版本号，保存后刷新酒馆页面生效；也可以直接在酒馆助手的变量管理里改。各组版本互不绑定：群里或帖子说哪个脚本更新到哪个版本，就改哪一项。不做自动更新和更新检查。MVU 按上游设计跟随最新版，仍按固定链接加载，不走这套回退和版本设置。

已经发出去的 V4.3.3 卡里写死的是旧链接，享受不到这些；加载器要随下一次正式发卡一起出去，之后才能只更资源不更卡。

### 发布资源补丁

```sh
pnpm card assets                 # 当前资源版本、标签、是否已标记发布、各 CDN 地址
pnpm card assets set 1.0.1       # 改资源版本，published 置回 false
pnpm card build --profile release
# 提交 dist/release/**，打标签 assets-v1.0.1 并推送（需开发组同意）
pnpm card assets verify          # 到 CDN 逐个入口核对，全部能访问才把 published 标成 true
```

标签提交必须包含 `dist/release/**`，规则同下文的卡发布。`verify` 只确认文件存在，不比对内容；发布前确认构建对应要发的源码。旧资源标签不移动，玩家改回旧版本号仍能用旧资源。

发布说明里写清：兼容哪些卡版本、玩家把「资源版本」改成什么、是否涉及变量结构变化。世界书正文、开场白、正则匹配规则和内嵌模板不随资源版本更新；变量结构或前端、自动化调用契约有变化时，要按卡版本规则处理，不能只发资源补丁。
