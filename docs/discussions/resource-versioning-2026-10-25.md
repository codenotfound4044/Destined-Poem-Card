# 程序资源与角色卡分开发版：讨论记录

日期：2026-10-25。

状态：独立发布程序资源的需求已经明确，本文记录讨论和后续实现建议；新版本体系尚未实现，也没有确定新的版本号或标签名称。

## 用户明确希望实现的用法

- 前端、自动化等程序资源可以发布新版本，不必同时升级角色卡版本、重新发布整张卡。
- 程序资源发布后，推送到酒馆可以使用带固定资源版本的 CDN 链接，不必一直使用本机链接。
- 例如角色卡继续使用原版本，只修了前端时，在帖子说明修改对应加载链接中的资源版本，玩家刷新后就能使用新前端，不必重新导入角色卡。
- 用户倾向于减少版本数量，不希望每条正则分别维护自己的版本号。不要把这个诉求理解成“程序资源必须跟随角色卡版本”。

修改已导入卡中的加载链接，仍会改变该卡的加载配置；这里“不更新角色卡”指不要求整卡重新发版、重新导入，也不因此覆盖世界书或聊天进度。

## 讨论中的建议与待定项

建议先采用“角色卡版本 + 一套自有程序资源版本”：首页、状态栏、自定义开局、自动化等共用程序资源版本，源码继续放在当前仓库。只修前端也可以发布资源补丁，卡版本保持不动。

这是一项建议，不是已经确认的最终设计。后续实现前仍需确定：

1. 前端与自动化共用一套程序资源版本，还是分别独立发版。用户明确要求它们与角色卡分开，但没有最终指定这两者之间的版本关系。
2. 玩家修改对应正则、脚本链接中的版本，还是增加一个统一的资源版本设置，让各加载入口共同读取。后者能减少重复操作，但目前没有实现，不能描述成已经可用。
3. 新资源版本的起点、Git 标签命名和发布路径。讨论中的 `1.0.1`、`assets-v1.0.1` 都只是示例，不是发布指令。

“版本统一”与“只改一次”不是同一件事。目前不同加载器分别存有 URL，即使 URL 使用相同版本，玩家也可能需要改多处。统一设置需要对应的加载入口支持；已有卡若沿用原入口，不能凭空读取新增设置。

## 当前实现与差距

- [release.json](../../release.json) 的 `version` 当前为 `4.3.3`，同时决定卡版本和自有资源的正式 CDN 标签。
- [tools/lib/version.mjs](../../tools/lib/version.mjs) 的 `cardIdentity()` 派生卡名、世界书名和标签；卡名与世界书名只带 major.minor。
- [tools/lib/card-source.mjs](../../tools/lib/card-source.mjs) 的 `assetOrigins()` 用 `cardIdentity(release).tag` 生成正式资源根，因此资源版本目前绑定卡版本。
- 同文件的 `assembleCard()` 将三个前端入口写进正则，将 Schema、自动化、地理加载地址写进脚本。普通正则定义和部分替换模板直接内嵌在卡里。
- [tools/workbench/ui/sync.js](../../tools/workbench/ui/sync.js) 的 `start()` 固定使用 `profile: "local"`；命令行已能传 `--profile`，但还没有独立资源版本模型。
- [tools/sync/server.mjs](../../tools/sync/server.mjs) 拦截未发布的 release 推送；现有推送是整卡与世界书覆盖，不是只更新加载链接。
- [tools/card.mjs](../../tools/card.mjs) 负责构建和装配；[tools/release.mjs](../../tools/release.mjs) 负责现有整卡发版。
- `packages/frontend/package.json` 的 `1.9.32` 与 `packages/automation/package.json` 的 `3.4.6` 是保留的包版本，目前不独立决定统一仓库构建的 CDN 地址。仅修改这两个字段，不会完成资源发布或切换酒馆中的加载链接。
- 开发标记目前根据装配后的卡 JSON 计算。前端和自动化主体通过 URL 加载，仅改主体代码时，标记可能不变；若完善统一资源构建标记，应考虑实际资源内容。

## 后续实现需要处理的内容

1. 将卡版本与程序资源版本分开记录，构建时分别用于卡身份和资源 URL。不要为了发布兼容的前端修复而连带修改卡名、世界书名。
2. 提供独立资源的打包、发布与结果核对流程。同仓维护不妨碍使用独立资源标签；是否单独构建前端或自动化，应与版本分组一起确定。
3. 工作台允许选择“本机测试资源”或“已发布资源”。选择已发布资源时使用对应固定版本 URL，并能看清即将使用的资源版本；不能只改版本字符串、实际文件却没发布。
4. 区分“整卡覆盖推送”与“只更新程序加载配置”。若支持后者，只更新选定加载器及必要设置，保留目标世界书、聊天进度和无关自定义内容，并保留备份、读回核对。
5. 如果采用统一资源版本设置，让相关加载器共同读取，明确玩家首次调整入口和后续只改版本的操作方式。
6. 发布说明写清“兼容哪些角色卡版本、修改哪个字段或哪几个链接、是否涉及变量结构变化”。

## 更新边界

- 界面调整、兼容现有变量结构的程序修复，适合独立发布资源。
- 世界书正文、开场白、正则匹配规则及内嵌替换模板，不会因为更新外链版本而自动更新；需要另行提供对应内容的更新方式。
- Schema 仍以 `packages/game/src/schema/` 为唯一来源。涉及变量结构或前端、自动化调用契约的变化，要核对兼容性；不能承诺任意资源版本都可与任意旧卡组合，也不要顺带实现旧存档迁移。
- 第三方依赖继续保留上游自己的版本或引用方式，不把工坊、MVU、角色库等第三方链接直接替换成自有资源版本。
- 已发布的旧标签与旧 CDN 链接保持原内容，不覆盖历史版本来实现更新。
- 当前 jsDelivr 地址读取 GitHub 标签对应的仓库文件；标签提交必须包含对应构建产物，只上传 GitHub Release 附件不足以提供这些链接。依照仓库授权规则执行实际发布。
