# 事件链与事件信号

命定的剧情事件是世界书里的 EJS 条目：条件满足时输出一段 `<event>`，告诉模型这一轮该怎么推进剧情、推进后要在 `<UpdateVariable>` 里写哪些变量；下一轮条目再根据这些变量决定输出哪一段。写新事件、改事件阶段或排查"事件不触发 / 卡阶段 / 信号丢了"前先读本页。

本页说的都在 `worldbook/命定之诗/事件/` 和 `packages/automation/` 里，引用的行为以当前源码为准。

## 一、三种写法

| 写法 | 状态存在哪 | 能否同时进行多个 | 现有例子 | 适合 |
| --- | --- | --- | --- | --- |
| 主线事件 | 全局事件槽 `事件.开启/结束/标题/阶段` | 否，同一时间只能有一个 | 群山回响、血姬、双子星的咏叹调 | 多章节、需要接管叙事的长线剧情 |
| 信号事件 | `事件.信号` 数组里的字符串 | 能，和主线事件、其他信号事件并行 | 斯芬克斯、神选者、瓷化密室 | 支线、分阶段奖励、可与主线并存的小剧情 |
| 世界事件 | `事件.<事件名>.*`，由 EJS 自己写 | 能 | 冰之歌 | 按等级或时间推进、全大陆可感知的背景大事 |

新事件先按这张表选写法。拿不准时：要"玩家接了就一路走下去"的选主线事件；要"随时可能碰到、不耽误别的剧情"的选信号事件；世界事件只在确实需要按时间线推进时用。

## 二、模型看得到什么

这是写事件时最容易误判的地方：

- **`事件` 整块对模型不可见。** `worldbook/命定之诗/变量/variables.ejs` 输出状态时 `_.omit(…, '事件')`，开启、阶段、信号、已完成列表都不会出现在 `<status_current_variables>` 里。模型只能通过 `<event>` 里的文字知道事件存在、该写什么变量。所以现有事件都会加一句"事件下属所有变量已完成初始化，即便不可见，也不允许重新初始化"，防止模型看不到就自己重建 `事件`。
- **当前事件和已完成列表只进扫描、不发给模型。** 自动化在生成前注入（`packages/automation/src/prompts/event-prompts.ts`）：`已完成事件`（内容为 `已完成事件A; 已完成事件B`）和 `事件`（内容为 `当前事件为<标题>，当前步骤为<阶段>`），两者都是 `position: 'none'` + `should_scan: true`。主线事件本体条目就是靠关键词 `当前事件为<标题>` 被点亮的。
- **事件进行中会额外插一句提示。** 有当前事件时还会注入 `事件提示`（`in_chat`、深度 0），要求模型按 `<event>` 发展剧情。
- **信号只给模型看一个假示例。** `[本体][事件]事件信号变量适配`（蓝灯，深度 1）在 `事件.信号` 是数组时输出 `信号: ['SEED_INIT']` 和"只追加、不删除"的更新规则；真实信号内容不会给模型看。

## 三、主线事件

### 变量与自动化

初始值在 `[InitVar]世界初始设定.yaml`：

```yaml
事件:
  开启: false
  结束: false
  标题: ''
  阶段: ''
  已完成事件: []
```

模型负责写 `开启`、`标题`、`阶段`、`结束`；`packages/automation/src/services/event.ts` 的 `processEvent` 在每轮变量更新结束时处理：

- `开启` 为真：缓存 `当前事件为<标题>，当前步骤为<阶段>`，下一轮注入扫描。
- `结束` 为真：把 `已完成事件<标题>` 追加进 `已完成事件`，再把 `标题`、`阶段` 清空，`开启`、`结束` 置回 false，清掉缓存与注入。结束不用模型自己清理字段。

### 条目结构

| 条目 | 激活 | 正文做什么 |
| --- | --- | --- |
| 入口 | 绿灯，场景关键词（可加次关键词收地点） | EJS 检查"未完成 + 槽位空闲 + 自定条件"，输出邀约剧情和开始时要写的变量 |
| 本体 | 绿灯，关键词 `当前事件为<标题>` | EJS 再核对 `标题`，按 `阶段` 输出对应章节，每章末尾写下一阶段或结束 |
| 人物 info | 绿灯，事件标题与人物名 | 普通设定，不写 EJS |

入口和本体放 `指定深度`、深度 1、角色系统，顺序沿用 114514；info 放 `角色定义之前` 或 `之后`。递归两项都设 true。

入口模板（照 `群山回响-入口.ejs` 简化）：

```ejs
<%_
{
  const title = '示例事件标题';
  const completed = getMessageVar('stat_data.事件.已完成事件', { defaults: [] });
  const busy = getMessageVar('stat_data.事件.开启', { defaults: false }) === true;
  const location = getMessageVar('stat_data.世界.地点', { defaults: '' });
  if (!completed.includes(`已完成事件${title}`) && !busy && location.includes('示例地点')) {
_%>
<event>
当{{user}}在示例地点活动时，安排……（邀约剧情、动机、可拒绝的出口）
<!-- SYSTEM_COMMAND_START -->
事件开始后，必须在<UpdateVariable>的JSON Patch中包含:
  { "op": "replace", "path": "/事件/开启", "value": true }
  { "op": "replace", "path": "/事件/标题", "value": "<%= title %>" }
  { "op": "replace", "path": "/事件/阶段", "value": "第一章" }
注意: 事件下属所有变量已完成初始化，即便不可见，也不允许重新初始化
<!-- SYSTEM_COMMAND_END -->
如{{user}}明确拒绝，必须在<UpdateVariable>的JSON Patch中包含:
  { "op": "replace", "path": "/事件/结束", "value": true }
</event>
<%_ } } _%>
```

本体模板：

```ejs
<%_ if (getMessageVar('stat_data.事件.标题') === '示例事件标题') { _%>
<%_ const stage = getMessageVar('stat_data.事件.阶段'); _%>
<%_ if (stage === '第一章') { _%>
<event>
……本章剧情要求……
**当……时，本章节结束。**
<!-- SYSTEM_COMMAND_START -->
本章节结束时，必须在<UpdateVariable>的JSON Patch中包含:
  { "op": "replace", "path": "/事件/阶段", "value": "第二章" }
<!-- SYSTEM_COMMAND_END -->
</event>
<%_ } else if (stage === '第二章') { _%>
<event>
……
事件结束时，必须在<UpdateVariable>的JSON Patch中包含:
  { "op": "replace", "path": "/事件/结束", "value": true }
</event>
<%_ } _%>
<%_ } _%>
```

要点：

- 标题要全卡唯一，`已完成事件<标题>` 和关键词 `当前事件为<标题>` 都靠它；改标题等于换成一个新事件，老存档的完成记录对不上。
- 阶段名在入口、本体、每章结尾三处逐字一致。
- 事件已失效（例如等级超出）时，可以让模型直接 `insert` 一条 `已完成事件<标题>` 到 `/事件/已完成事件/-`，入口从此不再出现（见群山回响入口）。
- 槽位只有一个：主线事件进行中，其他主线事件的入口会因为 `开启` 为真而不输出。

## 四、信号事件

### 协议

- `事件.信号` 是字符串数组，**只能追加**：`{ "op": "insert", "path": "/事件/信号/-", "value": "<信号>" }`。约束目前靠两处：适配条目里"不允许删除"的规则，以及 `packages/automation/src/runtime/command-policy.ts` 的命令过滤（设计上丢掉对整个 `信号` 的覆盖、删除、移动，放行追加）。
- 命令过滤现状：它按字符串精确匹配 `stat_data.事件.信号`，而当前锁定的 MVU（`references/upstream/mvu` 的 `extractJsonPatch`）把 JSON Patch 路径转成 `["事件"]["信号"]` 这种不带 `stat_data` 的方括号写法，两者对不上，JSON Patch 写法的覆盖和删除很可能拦不住；删除单个元素（`remove /事件/信号/0`）按设计本来也不拦。在修好之前，把"信号不会丢"当成提示词层面的约定，不要当成硬保证。
- 信号数组由事件 EJS 自己初始化：第一次渲染时 `setMessageVar('stat_data.事件.信号', [])`。数组存在后，适配条目才开始向模型说明信号规则。
- 信号名用"事件专属前缀 + 语义 + 后缀"，例如 `斯芬克斯支线_mid371`、`神选支线_<神>_xcb8`、`密室_in_event`。前缀要全卡唯一，判断"玩家走过哪条分支"用 `startsWith(前缀)`；后缀不必有意义，现有事件多用一段无规律字符，避免模型按语义猜出或编造信号。
- 信号写进 EJS 常量，`<event>` 里用 `<%= 常量 %>` 输出，不要手打两遍。

### 模板

```ejs
<%_ { // 用代码块包起来，避免和别的条目变量重名 _%>
<%_
if (!Array.isArray(getMessageVar('stat_data.事件.信号'))) {
  setMessageVar('stat_data.事件.信号', []);
}
const signals = getMessageVar('stat_data.事件.信号', { defaults: [] });
const PREFIX = '示例支线_';
const SIG_STARTED = `${PREFIX}st82`;
const SIG_DONE = `${PREFIX}dn47`;
_%>
<%_ if (!signals.includes(SIG_DONE)) { _%>
<%_ if (!signals.includes(SIG_STARTED)) { _%>
<event>
触发: ……（写清楚何时、何地允许触发，禁止强行控制{{user}}）
<!-- SYSTEM_COMMAND_START -->
后处理: 必须在<UpdateVariable>的JSON Patch中包含: { "op": "insert", "path": "/事件/信号/-", "value": "<%= SIG_STARTED %>" }
后处理: 必须在<UpdateVariable>的JSON Patch中包含: { "op": "insert", "path": "/事件/信号/-", "value": "<%= SIG_STARTED %>" }
<!-- SYSTEM_COMMAND_END -->
</event>
<%_ } else { _%>
<event>
……后续阶段……
<!-- SYSTEM_COMMAND_START -->
完成后处理: 必须在<UpdateVariable>的JSON Patch中包含: { "op": "insert", "path": "/事件/信号/-", "value": "<%= SIG_DONE %>" }
<!-- SYSTEM_COMMAND_END -->
</event>
<%_ } _%>
<%_ } _%>
<%_ } _%>
```

信号事件一般是一条蓝灯 EJS（深度 1、角色系统、顺序 114514），触发条件全写在 EJS 里。后处理指令重复写两遍是现有事件对付模型漏写信号的做法，保留即可。

### 进阶

- **按等级分阶段**（神选者）：阶段表写成数组，每段有 `minLevel/maxLevel` 和信号后缀；等级落在区间且没有该段信号时输出这一段，不要求按顺序走完。
- **EJS 自己维护状态**（瓷化密室）：信号只记"进入 / 完成 / 修好"这类里程碑，房间号这类细状态用 `setMessageVar` 写在 `事件.<事件名>` 下，再用 `matchChatMessages` 判断玩家本轮说了什么。
- **跨条目扩展**（神选者自定义神）：用聊天变量 `setvar(…, { scope: 'local' })` 登记扩展数据，主条目用 `getvar(…, { noCache: true, scope: 'local' })` 读取。

## 五、世界事件

冰之歌不占槽、不用信号：EJS 按等级首次满足时，把当时的 `世界.时间` 和楼层号写进 `事件.冰之歌.*`，之后用"当前楼层 − 触发楼层 ≤ 16"控制强提示持续多久；结局标记 `事件.冰之歌.异神已击败` 由模型用 `replace` 写入，EJS 再据此进入第三阶段。适合"到点就发生、玩家只是见证或参与"的背景大事。

## 六、EJS 与宿主注意事项

- **写的是哪一楼。** EJS 里不带 `withMsg` 的 `setMessageVar` 写入生成时的最后一楼（一般是玩家刚发的那条），MVU 随后在这一楼的基础上更新 AI 楼变量。要读"上一个 AI 楼的旧值"时，用 `getMessageVar(key, { withMsg: { id: -3 } })` 这类写法（见瓷化密室），并在注释里写明假设的楼层结构。
- **随机门槛会被重抽。** `Math.random()` 在每次渲染都会重新抽：重新生成、swipe 会重抽；开启"额外模型更新变量"时，事件条目名不带 `[mvu_update]`/`[mvu_plot]`，主回复和额外解析两轮都会带上、各渲染一次，可能主回复出现了事件而额外解析那轮没有，信号就没人写。随机只用来决定"第一次出现"，出现后改用不随机的条件续上，例如斯芬克斯的 `matchChatMessages('斯芬克斯')`，或者先写一个"已出场"信号。
- **代码块包起来。** 所有事件条目在同一次渲染里执行，最外层用 `<%_ { _%> … <%_ } _%>` 包住，避免 `const` 重名。
- **`<!-- SYSTEM_COMMAND_START/END -->` 和 `<!-- checkPoint -->`** 没有任何代码处理，只是给模型看的分隔标记；沿用即可，不要指望它们被脚本解析。
- **预设联动。** 命定专用预设有"事件链兼容"开关，让思维链先检查所有 `<event>` 再规划；这是预设侧行为，不影响世界书写法。

## 七、名称与 DLC 开关

事件默认以 DLC 发布，`启用: false`，玩家在首页 DLC 管理里开关（`packages/frontend/src/apps/home/services/DLCManagement.ts`）：

- 名称里 `[DLC][事件][事件名]` 是分组键，同一键下的所有条目一起开关；`事件名` 就是页面上显示的名字。
- 名称最后一对圆括号是作者信息，`作者-简介` 用第一个 `-` 分开显示。
- 关系标记：`[<X]` 前置（开启前要求 X 已开启，X 关闭时连带关闭）、`[!X]` 互斥、`[>X]` 替换。血姬入口的 `[<莉莉娅丝]` 就是要求先开角色 DLC 莉莉娅丝。
- 只给本事件用的人物 info 放进同一个 `[DLC][事件][事件名]` 组；人物本身是独立角色 DLC 时，用 `[<人物名]` 关联。
- 名称里不要带 `[mvu_update]`/`[mvu_plot]`，除非确定只想让它出现在某一轮。

## 八、新增一个事件

1. 按第一节选写法，定下唯一的标题或信号前缀。
2. 在 `worldbook/命定之诗/事件/<事件名>/` 下写正文（`.ejs`），人物 info 用 `.txt` 或 `.yaml`。
3. 在 `worldbook/命定之诗.yaml` 的 `[本体][事件]➡️事件开始` 与 `➡️事件结束` 之间加条目配置：名称按第七节，激活与位置按第三、四节，`启用: false`。
4. 需要新的状态字段时只放在 `事件.<事件名>` 下（`事件` 在 Schema 里是宽松的 record，不用改 `packages/game/src/schema/`）；不要改 `开启/结束/标题/阶段/已完成事件/信号` 的含义。
5. 检查：`pnpm card check`（文件已接入），`node tools/check-templates.mjs`（EJS 能编译，不会实际执行）。
6. 酒馆实测，每项看楼层变量和提示词预览：入口在条件满足时出现、不满足时不出现；开始后本体按阶段输出、入口消失；每次阶段推进变量写对；结束后 `已完成事件` 多一条、字段复位、入口不再出现；信号事件的信号只被追加；重新生成和 swipe；开、关"额外模型更新变量"各走一遍。没在酒馆里跑过的事件，不要写成已验证。
